SECTION 1 — PROJECT IDENTIFICATION
================================================================================

Name: VentureOS
Tagline: "Human-Controlled AI Business Operating System."
Location on disk: D:\Documents\claudehermespromt\ventureos (Confirmed — this
is where every file referenced in this document actually lives; see ADR-004
in docs/DECISIONS.md for why this is not the originally-instructed path).
Version: 0.1.0 (root package.json). License: UNLICENSED / proprietary.
Founder and sole final authority: Yiannis (PROJECT_CONTEXT.md, AGENTS.md).

Original idea: build a controlled system of AI agents that lets one founder
research, validate, create, launch, and operate small digital businesses
("ventures") end to end — inspired only by the publicly observable concept
of AI-managed side businesses. PROJECT_CONTEXT.md is explicit that VentureOS
"is inspired only by the publicly observable business concept of AI-managed
side businesses (see docs/SIDELOOT_COMPARISON.md) — no proprietary code,
branding, or trade secrets from any other company are used." Source:
PROJECT_CONTEXT.md lines 6-10. docs/SIDELOOT_COMPARISON.md (Confirmed,
read in full) explicitly states no founder-provided screenshots or notes
about "SideLoot" have ever been supplied and no research into it was
performed — the comparison document is presently an empty placeholder by
design, not a completed competitive analysis.

Current vision: a modular-monolith platform (Next.js dashboard + NestJS API
+ Temporal workflow engine + Postgres) where a fixed roster of 8 weighted
"board agent" roles plus a non-voting Decision Synthesiser review every
proposed venture, and the founder is the only party who can approve spend,
publication, or any irreversible action (docs/ARCHITECTURE.md,
docs/AGENT_ROLES.md, AGENTS.md rule 2).

Long-term objective (PROJECT_CONTEXT.md "Timeline" section):
  - Weeks 1-3: core technical + governance foundation (Phase 0/1).
  - 3 months: first end-to-end commercial pilot, first validated product
    ready for launch.
  - 12 months: repeatable revenue, controlled ad spend.
  - Long term: package and resell the platform itself, the agent system,
    workflow architecture, prompt framework, methodology, and a white-label
    version to other founders/agencies (this is now Implemented at the
    architecture level as Phase 8's SaaS resale build-out — see Section 14).

Intended users/customers: primarily the founder himself (single-workspace,
single-operator usage). Secondarily — per Phase 8's explicit "full SaaS
resale build-out" scope (docs/DECISIONS.md ADR-010, docs/EXECUTION_PLAN.md
Phase 8) — other founders/agencies who would run their own workspace (shared
multi-tenant instance) or their own fully separate self-hosted install
(docs/CUSTOMER_GETTING_STARTED.md, docs/DEPLOYMENT.md "Exportable/self-hosted
installs"). Status: Implemented at the data-model/API/UI level (registration,
plans, licensing, branding all real code); Not started commercially — zero
real customers, zero real payment processor, zero production deployment
(Confirmed — see Section 17).

Problems this project claims to solve: (1) the operational overhead of
running many small digital-product side businesses single-handedly; (2)
lack of trustworthy, evidence-backed opportunity research; (3) lack of
disciplined financial modelling before committing spend; (4) risk of an AI
system taking irreversible action without human sign-off; (5) lack of a
single auditable trail across research → decision → execution.

Expected commercial outcome (as stated in the project's own docs, not
independently validated by this document): a repeatable pipeline that can
launch and manage multiple small digital-product ventures under founder
control, plus — per Phase 8 — the option to resell VentureOS itself as a
licensed/self-hosted product to other founders. Status of that outcome:
Proposed/Planned only — no real product has ever been launched to a real
marketplace, no real revenue has ever been recorded, and no real customer
has ever paid for a VentureOS subscription (Confirmed via Section 17's
completion analysis and the mock-only findings throughout this document).

SECTION 2 — EXECUTIVE SUMMARY
================================================================================

What it is: a Turborepo monorepo (Next.js dashboard, NestJS API, Temporal
worker, PostgreSQL via Prisma, MinIO object storage) implementing an
numbered-phase build plan (the project's own internal Phase 0-8 numbering, per
docs/EXECUTION_PLAN.md and docs/ROADMAP.md). All numbered phases 0–8 are recorded in
the project's own documentation as "DONE" / "fully verified" (Implemented,
Source: docs/EXECUTION_PLAN.md, docs/ROADMAP.md, TODO.md).

How it works, end to end, per the founder-facing flow (docs/WORKFLOWS.md,
docs/CUSTOMER_GETTING_STARTED.md): a founder logs into a workspace, records
or triggers research (Research Connectors), the system computes an
Opportunity Score and a separate Profit Confidence Score for a candidate
venture (packages/scoring-engine), promotes it into a Venture Proposal, runs
it through 8 weighted "board agent" votes plus a non-voting Decision
Synthesiser (packages/policy-engine + packages/agent-runtime), requires the
founder's explicit approval (Approval Centre) before any product asset is
generated, generates a mock digital product + Etsy-shaped draft listing
(packages/product-studio), requires a second, distinct founder approval
before any "publication" step, publishes only against a mock Etsy adapter
(packages/marketplace-connectors), and tracks cost/revenue/experiments
against hard budget caps (packages/finance-engine). Every step is
Temporal-orchestrated (apps/worker) and every sensitive action is
append-only audited (apps/api/src/modules/audit).

What is completed / working, per the project's own claims cross-checked
against real source files, migrations, and test files present on disk: all
78 Prisma models exist (Confirmed via schema.prisma), 9 migration folders
exist (Confirmed via directory listing), 15 API modules exist with real
controllers/routes (Confirmed via grep of every module's *.controller.ts),
Temporal workflows exist for board-approval/product-listing/marketplace-
publication (Confirmed via apps/worker/src/workflows), and roughly 40+ test
files exist across unit/integration/e2e layers (Confirmed via `find`). One
specific, fully-reproducible passing-test artifact exists on disk right now:
apps/web/e2e/login-dashboard.spec.ts, whose real Playwright run is captured
in e2e-log3.txt, tail: "4 passed (4.8s)" across 4 named tests (redirect
unauthenticated visitors to /login; founder login → Command Centre; founder
navigation to audit/security pages; incorrect-password error). Everything
else's "passing" status is drawn from the project's own narrative log
entries in docs/EXECUTION_PLAN.md and the phaseN-*.log.txt files, which this
document treats as real historical evidence (quoted directly in Section 18)
but not as something independently re-executed during the writing of this

Source: docs/AGENT_ROLES.md, docs/AGENT_OUTPUT_CONTRACTS.md, packages/

CRITICAL FINDING, stated plainly up front: Confirmed — the entire agent
system is mock-provider-only end to end. `AI_PROVIDER` (packages/config/src/
env.ts line 57) is a Zod enum `z.enum(['mock', 'anthropic']).default('mock')`,
so the schema anticipates a real provider, but grepping packages/agent-
runtime/src for "anthropic" (case-insensitive) returns zero matches, and the
only files in that package are: approval-runner.ts, board-review-runner.ts,
decision-synthesiser.ts, mock-provider.ts, index.ts, and two test files.
There is no anthropic-provider.ts, no real-provider.ts, and no HTTP client to
any LLM API anywhere in the package. Every one of the 8 "board agents" and
the Decision Synthesiser is a deterministic TypeScript function operating on
already-persisted numeric scores — not a prompted language model call.
docs/AGENT_ROLES.md itself is explicit about this: "Mock provider (Phase 3
default, no live model calls)... no randomisation, no live research, so
results are reproducible." No later-phase doc claims this changed. Label:
Confirmed, mock-provider-only, no real LLM API wired in anywhere.

--- Decision Synthesiser ---
Purpose: summarise the board's outcome for the founder. Responsibilities:
render a recommendation that strictly mirrors the pre-computed
calculateBoardVotingResult() output. Inputs: DecisionSummary + BoardVote/
BoardVeto rows. Outputs: a synthesised recommendation string, never an
independent decision. Tools & permissions: read-only over board data.
Data access: workspace-scoped board review data. Decisions it CAN make: none
— docs/AGENT_ROLES.md is explicit: "must never vote, approve, override,
remove a veto, execute, or replace founder authority." Decisions it CANNOT
make: literally any binding decision. Dependencies: calculateBoardVotingResult.
Inter-agent comms: consumes the 8 voting agents' persisted outputs only.
Human approval points: irrelevant to it directly — the founder approves the
resulting ApprovalRequest, not the synthesiser's summary. Failure handling:
if the underlying voting result is unavailable, synthesis cannot proceed
(no independent fallback logic exists). Implementation status: Implemented,
mock/deterministic (packages/agent-runtime/src/decision-synthesiser.ts).

--- Chief Orchestrator ---
Unknown/Not found. No document (AGENT_ROLES.md, AGENT_OUTPUT_CONTRACTS.md,
ARCHITECTURE.md) and no source file names any "Chief Orchestrator" role or
component. The closest architectural equivalent is Temporal's workflow
definitions themselves (boardApprovalWorkflow etc.) acting as the procedural
orchestrator, plus BoardService.startReview() in apps/api triggering them —
but neither is framed anywhere as an agent role with its own AgentDefinition
row. Label: Unknown/Not found — this role from the master spec (if it names
one) does not appear to have been implemented as a distinct named agent.

--- The 8 voting board agents (table, per docs/AGENT_ROLES.md) ---
1. Market Intelligence Director — weight 15, no critical veto.
2. Product Strategy Director — weight 15, no critical veto.
3. Creative and Production Director — weight 10, no critical veto.
4. Finance and Risk Officer — weight 15, CRITICAL VETO (type FINANCE).
5. Growth Director — weight 10, no critical veto.
6. Compliance and Marketplace Policy Officer — weight 15, CRITICAL VETO
   (type COMPLIANCE).
7. Operations and Quality Officer — weight 10, CRITICAL VETO (type QUALITY).
8. Red Team and Security Officer — weight 10, CRITICAL VETO (type SECURITY).

Purpose (all 8, shared shape): provide a structured, schema-validated
"lens" opinion on a venture proposal before it reaches the founder. All 8
are seeded as real AgentDefinition + AgentPromptVersion ("v1") rows
(packages/database/src/seed.ts). Responsibilities: emit one AgentOutputSchema
-validated AgentOutput per Board Review. Inputs: the venture proposal's
persisted Opportunity Score/Profit Confidence Score/evidence data (Phase 2
output) — never live web research, never a live model call. Outputs: a
BoardVote row with decision (APPROVE|REVISE|REJECT), confidence 0-100,
summary, reasons[], supportingEvidenceIds[], assumptions[],
missingInformation[], risks[], requiredChanges[], estimatedImpact, veto
{active,type,reason}. Tools & permissions: AgentDefinition declares a
toolAllowlist and prohibitedActions per role (schema field, seeded) but —
per docs/THREAT_MODEL.md's "Excessive agent tool permissions" row — "no
runtime layer yet enforces an actual tool call against its role's allowlist
— still a real gap, not just a placeholder." Data access: workspace-scoped
opportunity/proposal data only. Decisions it CAN make: vote APPROVE/REVISE/
REJECT and, for the 4 critical-veto roles, raise a veto that blocks
regardless of score. Decisions it CANNOT make: execute anything, bypass the
founder, spend money, publish, or override another agent's veto. Dependencies:
Phase 2 scoring output must exist first. Inter-agent comms: none directly —
each agent's output is independent; only the voting-math function combines
them. Human approval points: the founder decides the resulting
ApprovalRequest, not any individual agent vote. Failure handling: fail-closed
— an invalid/missing output for any of the 8 marks the whole BoardReview
FAILED (BoardReviewInvalidOutputError), never silently treated as an
approval. Implementation status: Implemented, mock/deterministic
(packages/agent-runtime/src/mock-provider.ts). The Finance and Risk
Officer's veto logic is the one concretely exercised critical-veto path:
"fires a FINANCE veto when estimatedCostEur > 0 && isSpeculative &&
profitConfidenceScore < 40" (docs/AGENT_ROLES.md).

--- Research/market/pricing/financial-analysis/product-creation/marketing-
advertising/QA/security-compliance/deployment-monitoring "agents" ---
None of these exist as distinct AI-driven agent roles. What actually exists
in their place, all deterministic (non-LLM) code, not agents in the master-
spec sense:
  - "Research" -> packages/research-connectors mock adapter (fetchMock
    ResearchResult) — a scripted mock function, not an agent.
  - "Pricing/financial-analysis" -> packages/finance-engine pure functions —
    deterministic math, explicitly never delegated to an LLM (docs/
    FINANCIAL_MODEL.md: "All arithmetic goes through this package — agents
    (once they exist) may interpret the numbers in prose but never
    recompute them").
  - "Product-creation" -> packages/product-studio mock generator — templated
    file generation, not a generative-AI call.
  - "Marketing/advertising" -> Not started. FEATURE_ADVERTISING_ENABLED is
    false by default and no ad-creation code exists anywhere.
  - "QA" -> qa-checker.ts's evaluateQuality — a rule-based pure function
    (5 check types), not an agent.
  - "Security-compliance" -> packages/policy-engine's evaluateCorePolicies —
    deterministic policy checks, not an agent.
  - "Deployment-monitoring" -> Not started as an agent; health endpoints are
    plain code, no monitoring agent exists.
Label for all of the above: Confirmed as deterministic/mock code, not
agentic AI, per the explicit "no live model calls" language repeated across
docs/AGENT_ROLES.md, docs/DATA_ACQUISITION_CONTRACTS.md, and docs/
ETSY_API_INTEGRATION.md.

--- Board-of-directors voting process ---
Implemented, Source: packages/policy-engine/src/board-voting.ts
(calculateBoardVotingResult), schema models BoardReview/BoardVote/BoardVeto/
DecisionSummary (Confirmed present in schema.prisma). Mechanics: Approve =
full weight, Revise = half weight, Reject = zero weight; default 75%
weighted threshold; any active critical veto (Finance/Compliance/Security/
Quality) blocks regardless of score; a missing mandatory review blocks;
evidence quality below 70 blocks. Fully deterministic and unit-tested
(docs/POLICY_ENGINE.md). Live-verified real run: 8/8 APPROVE => weighted
score 100/75, no vetoes (docs/EXECUTION_PLAN.md Phase 3).

--- Final owner/founder approval ---
Implemented, Critical, Source: docs/APPROVAL_MODEL.md, ApprovalRequest/
ApprovalDecision models. The founder is the only party whose decision can
transition an ApprovalRequest out of PENDING. Every workflow signal-waits for
this decision (up to 7 days) before proceeding to any sensitive action. This
is the single mechanism that makes the entire mock-agent system safe to run
today even with zero real AI intelligence behind it — nothing the board
"decides" can execute without this separate, human, server-re-validated step.

SECTION 7 — WORKFLOWS
================================================================================
Source: docs/WORKFLOWS.md, docs/APPROVAL_MODEL.md, apps/worker/src/
workflows/. Each entry: Trigger / Inputs / Steps / Decision points / Approval
points / Outputs / Failure cases / Retry / Audit / Implementation status.

1. BUSINESS IDEA DISCOVERY / MARKET-NICHE RESEARCH (combined — the codebase
treats these as one connector-driven step). Trigger: founder clicks "Run
acquisition now" on a DataAcquisitionContract. Inputs: contract config
(rate limits, cost caps, freshness requirement). Steps: disable-switch check
-> rate-limit check -> cost-cap check -> mock adapter call
(fetchMockResearchResult) -> prompt-injection sanitisation -> freshness/
reliability scoring -> persist EvidenceArtifact. Decision points: none
requiring founder input (fully automatic once triggered). Approval points:
none — research itself is not a spend/publish action. Outputs: a
DataAcquisitionRun row + a real EvidenceArtifact. Failure cases:
BLOCKED_DISABLED, BLOCKED_RATE_LIMIT, BLOCKED_COST_CAP — all fail closed,
all persisted as a real run row, never silent. Retry: EXPONENTIAL_BACKOFF_3_
ATTEMPTS per contract config. Audit: research module actions logged.
Implementation status: Implemented (mock-only, zero live network calls).

2. OPPORTUNITY SCORING. Trigger: seed script or (future) a founder-triggered
re-score — Confirmed that only the seed path exists today; no UI/API action
recomputes scores after evidence changes (docs/SCORING_MODEL.md: "Nothing in
apps/api's Opportunities module recomputes scores... left for a later
phase"). Inputs: 11 opportunity factors + 10 profit-confidence factors.
Steps: calculateOpportunityScore() -> calculateProfitConfidenceScore()
(flags isSpeculative if opportunity>=70 and confidence<70) -> persist
OpportunityScore rows -> denormalize onto Opportunity. Decision/approval
points: none (pure calculation). Outputs: two OpportunityScore rows + updated
Opportunity fields. Failure cases: weights not summing to 100 throws at
module load (fail-fast, not per-call). Audit: not directly audited as its
own event type (score writes are part of the seed/promote flow). Status:
Implemented for the seed path; re-scoring on new evidence Not started.

3. AGENT VOTING (Board Review). Trigger: founder clicks "Run Board Review".
Inputs: VentureProposalVersion snapshot. Steps: Temporal boardApprovalWorkflow
starts -> runBoardReviewActivity -> 8 mock agents vote -> persist BoardVote/
BoardVeto -> calculateBoardVotingResult -> persist DecisionSummary ->
createApprovalRequestActivity. Decision points: veto triggers (Finance/
Compliance/Quality/Security), 75% weighted threshold. Approval points: none
yet at this step — approval happens next. Outputs: BoardReview + votes +
DecisionSummary + a new ApprovalRequest (PENDING). Failure cases:
BoardReviewInvalidOutputError on any invalid/missing vote (whole review
FAILED). Retry: Temporal proxyActivities retry policy. Audit:
BOARD_REVIEW_STARTED (apps/api, synchronous) + BOARD_REVIEW_COMPLETED
(apps/worker, via writeAuditEvent, added in ADR-008). Status: Implemented,
live-verified.

4. FINANCIAL ESTIMATION. Trigger: founder opens Finance Centre for a venture,
clicks "Generate forecast". Inputs: FinancialAssumption (auto-seeded with
DEFAULT_FINANCIAL_ASSUMPTIONS if none exists). Steps: calculateBreakEven +
calculateScenarios (LOW/BASE/HIGH) -> persist FinancialForecast + 3
FinancialScenario rows. Decision/approval points: none (informational).
Outputs: forecast + scenarios rendered in Finance Centre. Failure cases: none
observed beyond standard validation. Audit: FINANCIAL_FORECAST_GENERATED.
Status: Implemented, live-verified.

5. RISK EVALUATION. Not a standalone named workflow — risk assessment is
distributed across: board agent risks[] fields (per-vote), the Finance and
Risk Officer's veto logic, and evaluateCorePolicies' blocking checks (no
critical compliance/security/quality risk). No dedicated "Risk Evaluation"
workflow/module/page exists as its own artifact. Status: Implemented as a
cross-cutting concern, Not implemented as a standalone workflow.

6. OWNER APPROVAL. Trigger: any ApprovalRequest reaching PENDING. Inputs: the
bound artefact's current version/hash. Steps: founder reviews in Approval
Centre -> POST /approval-requests/:id/decide -> isApprovalValidForExecution
re-validated server-side -> ApprovalDecision persisted -> best-effort
Temporal signal sent. Decision points: APPROVE / APPROVED_WITH_CONDITIONS /
REJECTED / REVISION_REQUESTED / REVOKE. Approval points: this IS the approval
point (used identically at all 4 gates: VENTURE_PROPOSAL, PRODUCT_LISTING,
PUBLICATION, SCALE_DECISION). Outputs: state transition + audit event
(APPROVAL_DECIDED). Failure cases: hash/version drift -> forces EXPIRED,
decision rejected. Audit: APPROVAL_DECIDED every time. Status: Implemented,
live-verified across all 4 gates.

7. PRODUCT DESIGN / PRODUCT CREATION (combined — one pipeline in the code).
Trigger: founder clicks "Start Product Generation" (requires an APPROVED
VENTURE_PROPOSAL approval already). Inputs: approved proposal snapshot.
Steps: Temporal productListingWorkflow -> generateProductAssets (mock,
7 files across 6 asset kinds, uploaded via StorageProvider) -> evaluateQuality
(5 check types) -> LicenceRecord creation. Decision points: fail-closed gate
if no Phase-3 approval exists (ProductGenerationBlockedError). Approval
points: none yet at this exact step (approval happens after listing
generation, bundled). Outputs: Product/ProductVersion/ProductAsset +
QualityCheck rows, reaching QA_PASSED. Failure cases: ProductGenerationBlocked
Error. Audit: PRODUCT_GENERATED (worker-side, ADR-008). Status: Implemented,
live-verified.

8. QA (Quality Assurance). Trigger: automatic, immediately after product
generation, same workflow. Inputs: generated assets. Steps: evaluateQuality
checks COMPLETENESS/FILE_INTEGRITY/NAMING_CONVENTION/DUPLICATE_ASSET/
LICENCE_COMPLETENESS. Decision points: any FAILED check blocks listing
generation (ListingGenerationBlockedError). Outputs: QualityCheckResult rows.
Status: Implemented, live-verified (100% pass on the seeded example).

9. MARKETPLACE LISTING / PRICING (combined). Trigger: automatic, same
workflow, once QA_PASSED. Inputs: approved product package. Steps:
generateListing() (deterministic title/description/tags/category/price/
images/files) -> evaluateSeoContent(). Decision points: Gate 4 (Listing
Validation) checks. Approval points: bundled into the same PRODUCT_LISTING
ApprovalRequest as product design above. Outputs: Listing/ListingVersion +
SEOEvaluation + a PublicationAttempt row forced to BLOCKED_NO_LIVE_
INTEGRATION (Phase 4 — no live publish path exists at this stage by design).
Status: Implemented, live-verified (SEO 100/100 on the seeded example).

10. MARKETING MATERIAL GENERATION / AD CREATION. Not started. No package,
module, or UI page generates marketing copy, ad creative, or ad-campaign
configuration anywhere in the codebase. FEATURE_ADVERTISING_ENABLED=false
by default and no code path reads it to gate an actual ad-creation feature
(the flag currently has nothing built behind it to gate). Status: Not
started/Planned only.

11. PUBLISHING. Trigger: founder clicks "Start publication (mock adapter)"
(requires APPROVED PRODUCT_LISTING approval). Inputs: approved listing
version. Steps: Temporal marketplacePublicationWorkflow -> prepareListing
ForPublication (mock draft create + image/file upload, idempotent) -> if
READY_FOR_PUBLISH, requestPublicationApproval (third, distinct approval
gate) -> signal-wait -> publishListing on founder APPROVE. Decision points:
BLOCKED_NO_APPROVAL/BLOCKED_DISABLED/BLOCKED_RATE_LIMIT fail-closed checks.
Approval points: the PUBLICATION ApprovalRequest, hash-bound separately from
PRODUCT_LISTING. Outputs: PublicationAttempt (SUCCEEDED) with a real mock
listing URL (https://mock.etsy.example/listing/<id>). Failure cases: mock-
adapter error -> FAILED status with errorMessage, idempotency-key conflict
-> IdempotencyKeyConflictError. Retry: FAILED idempotency keys retried in
place, never duplicated. Audit: PUBLICATION_PREPARED, PUBLICATION_APPROVAL_
REQUESTED, PUBLICATION_PUBLISHED (or PUBLICATION_FAILED) — all worker-side
via writeAuditEvent (ADR-008 fix). Status: Implemented, mock-only,
live-verified end to end.

12. SALES TRACKING. Trigger: founder manually records a RevenueEntry via the
Finance Centre. Inputs: gross amount, category. Steps: server computes
netRevenueEur (gross minus marketplace fee, payment fee, listing fee, VAT,
refunds) — never trusted from client input. Decision/approval points: none.
Outputs: RevenueEntry row, forecast-vs-actual comparison updates live. Audit:
REVENUE_RECORDED. Status: Implemented as manual entry only — there is no
automatic sales-tracking integration pulling real marketplace order data
(consistent with mock-only marketplace publishing — there are no real sales
to track).

13. CUSTOMER SUPPORT. Not started. No support-ticket model, module, or UI
page exists anywhere in the reviewed schema or apps/ source. RefundRequest
exists as a bare Prisma model (Phase 7) but Requires verification whether
any workflow/UI creates or resolves one — none was found in any grepped API
route. Status: Not started/Planned only.

14. PERFORMANCE ANALYSIS. Partially implemented, distributed: forecast-vs-
actual comparison (compareForecastToActual) is the closest real feature —
it diffs a forecast's BASE scenario against real recorded revenue and
returns forecastErrorEur/forecastErrorRate. No broader "performance
dashboard" (traffic, conversion rate, ad ROAS, etc.) exists, consistent with
there being no real marketplace/ad data to analyze. Status: Partially
implemented (financial performance only).

15. PRODUCT OPTIMISATION. Represented only via the Experiment lifecycle
(createExperiment -> startExperiment -> recordExperimentResult ->
recordExperimentDecision, DRAFT->RUNNING->DECIDED). No automatic
"optimise this listing's SEO/pricing" feature exists — experiments are
manually created and manually recorded by the founder today. Status:
Implemented as a manual experiment-tracking tool; Not implemented as an
automated optimisation loop.

16. PRODUCT RETIREMENT. Not started. No workflow, model field (e.g. a
"RETIRED" product/listing status), or UI action for retiring a product or
listing was found anywhere in the schema or source reviewed. KILL is a
valid ExperimentDecision value (alongside ITERATE/HOLD/SCALE) which reduces/
holds spend, but this is not the same as a formal product-retirement
workflow (unpublishing a live listing, archiving assets, etc.). Status: Not
started/Planned only.

17. SCALING. Implemented narrowly as Gate 6 (Scale Decision): a SCALE
ExperimentDecision requires an APPROVED SCALE_DECISION ApprovalRequest
before it can be recorded; KILL/ITERATE/HOLD never require approval since
they only reduce/hold spend. This is the entire "scaling" mechanism that
exists in code today — there is no broader infrastructure-scaling or multi-
region-scaling workflow (consistent with the single-instance, modular-
monolith architecture, Section 5). Status: Implemented (Gate 6 approval
mechanics only), live-verified (docs/EXECUTION_PLAN.md Phase 7).

18. FAILURE RECOVERY. Distributed across several real mechanisms rather
than one named workflow: (a) Temporal's own durable-execution/retry model
for activities (proxyActivities with retries/timeouts); (b) withIdempotency's
FAILED-key-retried-in-place behavior for marketplace writes (packages/
marketplace-connectors); (c) fail-closed blocking (BLOCKED_* statuses)
recorded as real rows rather than thrown exceptions the founder can't see;
(d) hash-drift detection forcing EXPIRED approvals rather than executing
against stale data. Not yet exercised live, per docs/WORKFLOWS.md: "the
signal-wait timeout path and worker-restart-mid-workflow recovery — both
follow directly from Temporal's guarantees but haven't been explicitly
forced in a test." Status: Implemented (idempotency/fail-closed paths,
tested); Requires verification (Temporal's own crash-recovery guarantees,
never explicitly forced/tested in this project).

Prompt injection protection: sanitizeUntrustedContent (packages/research-

payload before persistence. Real test evidence exists:
prompt-injection-sanitizer.test.ts (unit) plus an integration test in

payload and asserts the dangerous instruction text never appears in the

SECTION 16 — DECISIONS AND RATIONALE
================================================================================
Primary source: docs/DECISIONS.md, 11 ADRs, read in full. Secondary:
docs/ASSUMPTIONS.md, PROJECT_CONTEXT.md.

ADR-001: Hand-rolled session auth instead of Better Auth/Auth.js. Rationale:
both libraries assume a single Next.js app owns auth; VentureOS deliberately
splits web/API so NestJS is the sole authorization source of truth.
Consequence accepted: MFA/OAuth/account-recovery become bespoke future work.

ADR-002: Modular monolith, not microservices. Rationale: single founder,
single workspace, tight budget — no operational benefit to microservices at
this scale.

ADR-003: Deterministic engines (finance/scoring/policy) built as standalone
packages ahead of their consuming features. Rationale: correctness matters
most here; unit-testing them independent of any UI/AI provider lets later
phases consume already-verified logic. Risk accepted: minor rework chance if
later domain modeling changes the interface (judged low, and in practice
this did not materialize as a major rework).

ADR-004: Project location changed mid-build. The founder's original
instruction placed the project inside "D:\Documents\hermes ai agent," found
to contain unrelated internal Hermes runtime state; relocated per founder
direction, landing at D:\Documents\claudehermespromt\ventureos due to a
sandbox folder-picker limitation.

ADR-005 / ADR-006: The apps/api dev-runner saga (full detail in Section 15).
Final state (ADR-006): nest start --watch --webpack, with every consumed
workspace package given a real tsc build to dist/, and turbo's dev task
depending on ^build (with --parallel dropped from the root dev script since
it ignored the dependency graph).

ADR-007: Phase 6 marketplace pilot runs mock-only — no real Etsy account
connected. Founder's exact quoted instruction (2026-07-14): "I WILL NOT
CONNECT MY ETSY ACCOUNT NOW, CONTINUE TO FINISH MY AGENCY." This is
characterized in the doc itself as "a real, load-bearing decision, not a
placeholder default" — master spec section 21 requires any "verified working
with a real account" claim be literally true before it's written anywhere.
Consequence: MarketplaceAccount.mode is 'MOCK' for every row; the schema
supports a future 'REAL' mode but nothing sets it.

ADR-008: Temporal worker activities get their own audit-write path,
duplicating AuditService.record() without NestJS DI. Root cause: apps/worker
has no NestJS DI container, so its activities bypassed AuditService
entirely, leaving Phase 3/4/6 workflow-triggered actions unaudited for their
intermediate steps. Founder was presented 3 options (fix Phase 6 only; fix
all three phases; document and defer) and explicitly chose "Fix all three
phases now." Trade-off accepted: audit-write logic is now duplicated in two
places (apps/api's AuditService and apps/worker's writeAuditEvent()) — a
known, accepted maintenance cost rather than restructuring apps/worker to
have a DI container.

ADR-009: Two real Phase 7 bugs found via testing and live verification. Bug
1 — Gate 6 packageHash scheme mismatch (would have permanently blocked every
SCALE approval). Bug 2 — serverApiFetch crashing on NestJS's empty-body null
responses. Pattern drawn explicitly in the doc: "code review and unit tests
on individual functions are necessary but not sufficient" — live browser
verification at every phase boundary exists specifically to catch this class
of integration-boundary bug.

ADR-010: Phase 8 billing/subscriptions run mock-only — no real payment
processor connected. Founder-confirmed via the "full SaaS resale build-out"
instruction. Follows the identical pattern ADR-007 established for
marketplace: build real lifecycle/enforcement logic against a mock provider
first, so a real processor is later an additive change behind @ventureos/
billing's existing interface.

ADR-011: Four real Phase 8 bugs found via the verification suite (seed.ts
TS18048; three @ventureos/billing TS2742/noUncheckedIndexedAccess errors
that had been silently skipped until pnpm install linked the new package in
for the first time; a missing apps/web ESLint config that hid a react/no-
unescaped-entities backlog). Pattern drawn explicitly: 3 of the 4 bugs were
only reachable because a tooling gap (unlinked package, missing ESLint
config) had been silently suppressing an entire category of checks — "a
'clean' verification run only proves what it actually executed, not what it
silently skipped."

Other explicit decisions (docs/ASSUMPTIONS.md, PROJECT_CONTEXT.md):
package-manager/framework versions assumed at write-time (pnpm 9.x, Node 22
LTS, TypeScript 5.6, NestJS 10.x, Next.js 14, Prisma 5.x, Temporal SDK
1.11.x) without independent verification of interoperability inside the
original sandbox; a minimal two-role RBAC model (FOUNDER/VIEWER) for Phase 1
rather than the fuller eventual role set; session tokens stored plaintext
with a unique index as an accepted Phase-1 gap; GitHub Actions assumed as CI
provider without explicit founder confirmation; specific pinned Docker image
tags chosen for reproducibility, unverified in the original sandbox; a
single workspace slug "ventureos-default"; founder default timezone Europe/
Athens (inferred, not confirmed); white-labeling and budget-cap defaults
(Month 1 <=~EUR100, Month 3 <=~EUR250/month, steady state ~EUR300-500/month)
recorded in PROJECT_CONTEXT.md as founder-set commercial defaults for the
Phase 1 pilot slice.

Risk register. Each: Risk ID / description / category / likelihood / impact
/ severity / mitigation / contingency / owner / status.

RISK-001. Uncommitted git history (~90% of the project has zero commit
coverage). Category: Technical/Operational. Likelihood: High (any accidental
`git checkout`, disk failure, or working-tree reset could destroy it right
now). Impact: Severe (total loss of 7 phases of work, no rollback point).
Severity: Critical. Mitigation: commit immediately in logical phase-grouped
commits (RW-C1, Section 19/25). Contingency: none exists today — this IS the
contingency gap. Owner: founder/whoever has filesystem access. Status: Open,
highest priority.

RISK-002. No staging/production deployment ever tested. Category:
Technical/Operational. Likelihood: High (untested until attempted).
Impact: Medium-high (first real deployment will likely surface new
environment-specific bugs, similar to the many real local-environment bugs
already found across Phases 1-8). Severity: High. Mitigation: build and
exercise a staging environment before production (Template Phase 11,
Section 20). Contingency: budget time for a real bug-fixing pass during
first staging deployment, mirroring the pattern already established locally.
Owner: whoever performs the deployment. Status: Open.

RISK-003. Financial — budget-cap enforcement never exercised against a real
non-zero cost. Category: Financial. Likelihood: Medium (will definitely be
tested the first time a real AI provider or real ad spend is enabled).
Impact: Medium (could allow an unintended overspend if the enforcement logic
has an untested edge case). Severity: Medium-high. Mitigation: test
assertWithinBudget/chargeToBudget against a real non-zero cost in a
controlled staging environment before enabling any real spend in production.
Contingency: manual spend monitoring as a backstop during initial real-cost
rollout. Owner: whoever enables the first real-cost integration. Status:
Open.

RISK-004. Legal — GDPR readiness gap. Category: Legal/Compliance.
Likelihood: Low today (no real customer data exists), High if real customers
are onboarded before this is fixed. Impact: Severe (regulatory exposure).
Severity: High (conditional on commercial launch). Mitigation: build data-
subject-request flows (RW-M2) before collecting any real customer personal
data; do not launch commercially with real customer data until this is
closed. Contingency: legal counsel review before any real customer
onboarding. Owner: founder. Status: Open, not urgent until commercial launch
is imminent.

RISK-005. Legal/Marketplace — Etsy ToS compliance, since the mock adapter's
shapes are modeled on researched-but-unverified-live API behavior. Category:
Legal/Marketplace. Likelihood: Medium (API details "drift between doc
snapshots" per docs/ETSY_API_INTEGRATION.md's own caveat). Impact: Medium
(a real integration built against stale API assumptions could fail or
violate ToS). Severity: Medium. Mitigation: re-verify the real Etsy Open
API v3 documentation at the time a real account is actually connected, not
relying on the Phase 6 research snapshot alone. Contingency: the existing
fail-closed/idempotency/approval-gate architecture (Section 5/11) would
contain the blast radius of any single failed real call. Owner: whoever
implements the real Etsy client. Status: Open, dormant until Etsy mode
changes from mock.

RISK-006. Marketplace — Etsy API changes over time (rate limits,
authentication details, endpoint shapes) between when they were researched
(2026-07-14) and whenever a real integration is actually built. Category:
Marketplace. Likelihood: Medium-high (APIs evolve). Impact: Medium.
Severity: Medium. Mitigation: treat docs/ETSY_API_INTEGRATION.md as a
starting point, not a guarantee, at real-integration time. Owner: same as
RISK-005. Status: Open, dormant.

RISK-007. Security — no independent security review has ever occurred; the
entire threat model (docs/THREAT_MODEL.md) is self-authored by the same
process that built the features it assesses. Category: Security.
Likelihood: Medium (self-review reliably misses some classes of issue).
Impact: High (unknown unknowns in a system that will eventually handle real
approvals/spend). Severity: High. Mitigation: commission or perform a
genuine external security review before production (RW-F6). Contingency:
the layered fail-closed architecture (approval hash-binding, budget guards,
RBAC) provides defense-in-depth even if one specific control has an
undiscovered flaw. Owner: founder. Status: Open, required before production.

RISK-008. AI — prompt injection against research content. Category: AI/
Security. Likelihood: Medium (any real-world content source could attempt

maintains packages/research-connectors. Status: Mitigated, monitor for
evasion.

RISK-009. AI — mock-vs-real provider risk: if a real AI provider is ever

MONTHLY_LIMIT_EUR env vars all exist and the recording mechanism
(recordModelUsage) is real from day one — only the actual charge-blocking

Owner: whoever connects a real AI provider. Status: Open, dormant.

RISK-011. Operational — the CI workflow targets branch `main` but the local
